# 编辑器键位统一标准

一个人在编辑器里需要的操作是固定的，换编辑器不该换肌肉记忆。这份文档定一套跨编辑器的标准，
并记录每个编辑器离标准还差多远。

盘点的骨架来自《程序员修炼之道》20 周年版 Topic 18「Power Editing」——它列了一组
不该靠鼠标和菜单完成的能力，正好可以当作「一个编辑器至少要能干什么」的检查表。

> 范围说明：这些操作大多**不经过 Karabiner**，但同样属于「这台机器的键位」。
> 已登记进 `custom/apps.yml`，会出现在 `keymap.html` 和练习页里。

## 一、数据来源与可信度

**Zed 键位取自官方仓库，不是从二进制猜的。**

| 来源 | 作用 |
|---|---|
| [`assets/keymaps/default-macos.json`](https://github.com/zed-industries/zed/blob/main/assets/keymaps/default-macos.json) | 绝大多数绑定 |
| [`assets/keymaps/macos/vscode.json`](https://github.com/zed-industries/zed/blob/main/assets/keymaps/macos/vscode.json) | `settings.json` 里 `base_keymap: VSCode` 叠加的一层 |
| `~/.config/zed/keymap.json` | 自己改的，表里标「自定义」 |

**VSCode 那层只有约 20 条**，它没碰 `⌘D`、复制行、移动行、删除行——所以 Zed 基本可以当
macOS 默认看。（一度以为它会大改，是错的。）

以下两点**未经实证**，用到时请自行确认：
- **IntelliJ 的键位**是凭记忆写的，这台机器上没装，无法核对。
- **书里的清单是我用自己的话复述的**，没拿到逐字原文（O'Reilly 付费墙）。需要精确引用请翻实体书。

## 二、标准怎么定的

两条原则，按顺序适用：

**1. 行编辑块跟 JetBrains 现代 macOS 约定。**
这是从 JetBrains 带过来的肌肉记忆，值得保留——而且它比 VS Code / Zed 的出厂设定更自洽：

```
⌥↑ / ⌥↓     扩展 / 收缩选择      ← 「⌥ = 放大一级单位」，和 ⌥←→ 按词同一条原则
⌥⇧↑ / ⌥⇧↓   上移 / 下移一行
```

VS Code 和 Zed 出厂都是 `⌥↑↓` 移动行、`⌥⇧↑↓` 复制行，**两边都已改过来**。

> 历史注记：JetBrains 更早的 Mac keymap 用 `⌘W` / `⌘⇧W` 做扩展/收缩选择。
> 那套没被继承——`⌘W` 在 macOS 上是「关闭窗口」的通用约定，抢它代价太大。
> 现代 JetBrains macOS keymap 自己也换成了 `⌥↑↓`。

**2. 其余跟 VS Code / Zed 共识。**
这两家在注释、多光标、跳定义、大纲、重命名上几乎完全一致，而 IntelliJ 是那个离群的。
既然主力已经从 JetBrains 换成 Zed，就以多数派为准。

## 四、Hyper 层负责哪一段

书里 12 类能力，**只有第 1 类「按字符/词/行移动与选择」属于 Hyper 层的战场**，
而 Hyper 层几乎全部投入在这一类上。这不是失衡，是分工：

| | 归谁管 | 为什么 |
|---|---|---|
| 高频、要连按、手不能离开主键区 | **Hyper 层** | 移动光标一天几百次，`⇪H/L` 实测 87/90 次 |
| 单个 `⌘` 组合能覆盖 | **编辑器自己** | `⌘/`、`⌘Z`、`⌘D` 已经够近，Hyper 化没有收益 |
| 双修饰键 + 方向键 | **候选** | 如 `⌘⌥↑↓` 多光标——形状正是 Hyper 擅长消灭的 |

目前唯一明确划算的候选是**多光标 `⌘⌥↑↓`**：书里点名，形状难按，且 Zed / VS Code 一致。

## 六、后续想做：从 apps.yml 生成各家编辑器的配置文件

调研结论：**这类工具不存在。** 生态里全是「把 A 模仿成 B」的兼容层
（Zed 的 `base_keymap`、VS Code 的 keymap 扩展、IntelliJ 的 keymap 预设），
没有一个是「从一份声明生成 N 份配置」。旁证是 JetBrains 自家的
[IJPL-119533](https://youtrack.jetbrains.com/issue/IJPL-119533/Provide-a-unified-keymap-across-all-JetBrains-IDEs)
「跨全部 JetBrains IDE 统一 keymap」至今未解决——同一家公司同一套平台都没做成。

而这个项目已经走了大半：`apps.yml` 是声明式单一事实源，`bin/keymap.py` 已经在消费它。
缺三样：

**1. 抽象能力 ID + 各家动作名对照表。** 现在条目直接写编辑器自己的动作名，
生成器需要的是 `cap: move-line-up` 加一张表：

```yaml
move-line-up:
  zed:      editor::MoveLineUp
  vscode:   editor.action.moveLinesUpAction
  intellij: MoveLineUp
```

**上面第三节的合规表就是这张对照表的内容**，只差变成机器可读的形式。

**2. 键位记法翻译**（纯机械）：

```
标准     cmd+shift+d
Zed      cmd-shift-d
VS Code  shift+cmd+d
IntelliJ shift meta D
Obsidian {"modifiers":["Mod","Shift"],"key":"D"}
```

**3. 四个输出器。** Zed / VS Code / Obsidian 是 JSON，IntelliJ 是 XML。

### 必须先解决的问题：别覆盖手写内容

`~/.config/zed/keymap.json` 里有大段注释解释「为什么这么绑」，VS Code 的
`keybindings.json` 有上百条跟编辑无关的绑定。整文件重写会全部丢掉。
方案是**只管一个受控区段**：

```jsonc
// >>> generated by capslock, do not edit <<<
// <<< end generated >>>
```

### 规模与真实成本

核心约 200 行 Python，能复用 `keymap.py` 的大部分解析。
**成本不在代码，在那张对照表**——每加一个编辑器都要把它的动作名系统摸一遍。

而且对照表**没法自动生成**：各家「动作」的颗粒度不同（Zed 的
`SelectLargerSyntaxNode` 是语法树节点，IntelliJ 的 `EditorSelectWord` 是词法+语法混合，
VS Code 的 `smartSelect.grow` 又是一套），多数情况行为相同但不是同一个东西。
语义对齐必须人来拍板「我认为这三个足够等价」，机器只能做记法转换。

**建议的第一步**：先只出 Zed 一家，跑通「区段生成 + 手写保留」这个机制，
验证可行再铺开。
